================================================================================
1. PROJECT OVERVIEW
================================================================================

DocChat is a full-stack web application that lets a user upload their own
documents (PDF, Word, PowerPoint, Excel or text) and ask questions about them
in plain English. Every answer is written only from the content of the
uploaded document and shows the page numbers it came from.

It uses a technique called Retrieval-Augmented Generation (RAG):

  1. RETRIEVAL  - find the few passages of the document that are most
                  relevant to the question (using embeddings + vector search)
  2. AUGMENTED  - put those passages into the prompt sent to the AI model
  3. GENERATION - the model (Google Gemini) writes the answer from them

On top of question answering, DocChat also:
  - summarises documents (overview, key takeaways, glossary)
  - generates multiple-choice quizzes and viva (oral exam) questions
  - draws a concept map of the main ideas and how they relate
  - answers one question across several documents (workspaces)
  - compares two documents
  - supports voice input and read-aloud, PDF/Markdown export, light/dark themes

Target users: students preparing for exams and vivas, and anyone who needs to
find information quickly in long documents (notes, papers, manuals, reports).

2. PROBLEM STATEMENT AND OBJECTIVES
================================================================================

Problem
-------
- Searching long documents with Ctrl+F only works if you know the exact words.
- General AI chatbots answer from what they learned in training, not from YOUR
  document, and can confidently make things up ("hallucinate").
- Pasting a whole document into a chatbot is slow, costly, hits length limits,
  and gives no way to check where an answer came from.

Objectives
----------
1. Let users upload documents in common formats and extract their text page by
   page.
2. Answer questions using only the relevant parts of the document, with page
   citations so the user can verify the answer.
3. Say clearly when the document does not contain the answer.
4. Help students study: summaries, quizzes, viva questions, concept maps.
5. Support questions across multiple documents.
6. Keep each user's data private and secure.
7. Stay responsive: stream answers and process uploads in the background.

10  Export                  Chat to PDF / Markdown; complete study guide PDF.

11  Usage / Analytics       Questions asked, documents/pages/chunks indexed,
                            quiz performance, daily activity chart, average
                            model latency, storage used.

12  Theme                   Light, dark, or follow the system.

6.3 FLOW: UPLOADING AND PROCESSING A DOCUMENT (ingestion pipeline)
------------------------------------------------------------------

 User selects file
        |
        v
 [Frontend] check extension (.pdf .docx .pptx .xlsx .xls .txt) and size <= 20 MB
        |
        v
 POST /documents/upload (multipart/form-data, JWT)
        |
        v
 [Multer] validate extension, save file as uploads/<random-uuid>.<ext>
        |
        v
 INSERT INTO documents (status = 'processing')
        |
        v
 Respond 202 Accepted  -------> frontend shows "Processing", polls every 3 s
        |
        |  (background, request already finished)
        v
 EXTRACT text page by page
   PDF  -> pdf-parse  (one entry per page)
   DOCX -> mammoth    (one "page")
   XLSX -> SheetJS    (one "page" per sheet)
   PPTX -> JSZip      (one "page" per slide, reads <a:t> text runs)
   TXT  -> read file  (one "page")
        |
        v
 CHUNK each page: 2000 characters, 200-character overlap
        |               (no chunk crosses a page boundary)
        v
 EMBED chunks with gemini-embedding-001
   - batches of 25 texts per API call
   - retry with back-off on 429 (rate limit) / 503 (busy)
   - result: one 3072-number vector per chunk
        |
        v
 INSERT INTO chunks (id, document_id, chunk_index, page_number,
                     chunk_text, embedding)       -- one transaction,
                                                  -- 100 rows per INSERT
        |
        v
 UPDATE documents SET status = 'ready', page_count, chunk_count
   (on any error: status = 'failed', error_message = readable reason)

6.4 FLOW: ASKING A QUESTION (retrieval + generation)
----------------------------------------------------

 "Where does the Calvin cycle take place?"
        |
        v
 POST /chats/:documentId/message/stream
        |
        v
 Verify JWT -> document belongs to user? -> status = ready?
        |                                    (else 404 / 400)
        v
 Embed the question -> 3072-number vector q
        |
        v
 SQL: among this document's chunks, order by cosine distance to q, LIMIT 4
        |
        v
 Send SSE event "sources" (page numbers + snippets + scores)
        |
        v
 Build prompt:
   "You are a helpful assistant answering questions about a document.
    Use ONLY the context below... If the answer is not present, say
    'I don't have enough information in this document to answer that.'
    Context: [Chunk 1 - Page 2] ... [Chunk 4 - Page 1] ...
    Question: ...  Answer:"
        |
        v
 Gemini generateContentStream (thinking set low, model fallback)
        |
        +--> each piece of text -> SSE event "delta" -> shown immediately
        |
        v
 Save question + full answer + sources to messages table
        |
        v
 SSE event "done"  -> frontend shows the source list and Read Aloud

6.5 FLOW: SUMMARY (map-reduce for long documents)
-------------------------------------------------

 Load all chunks of the document
        |
        +-- 15 chunks or fewer --> one call: whole text -> JSON summary
        |
        +-- more than 15 chunks
               |
               v
          MAP: split into groups of 8 chunks
               summarise each group (4 groups at a time, in parallel)
               |
               v
          REDUCE: combine the section summaries -> one call -> JSON:
               { executiveSummary, difficulty, keyTakeaways[], glossary[] }
        |
        v
 reading time = total words / 200 (minutes)
        |
        v
 Save in document_summaries (cached: next open is instant;
 "Regenerate" forces a new one)

6.6 FLOW: QUIZ
--------------

 Choose type (MCQ / viva), difficulty, number of questions
        |
        v
 Sample up to 15 chunks evenly from start to end of the document
        |
        v
 Prompt Gemini for JSON (responseMimeType = application/json)
        |
        v
 Parse safely (strip ``` fences, accept {questions:[...]} or [...]),
 validate: question text, >= 2 options, correctAnswer is a valid index
        |
        v
 Save to quizzes (questions as JSONB) -> show one question at a time
        |
        v
 Submit -> server compares answers with correctAnswer -> score saved

------------------------

 SIGN UP:  email lower-cased -> duplicate check -> bcrypt.hash(password, 10)

7.4 THE VECTOR SEARCH QUERY
---------------------------

 WITH candidates AS MATERIALIZED (
   SELECT id, document_id, page_number, chunk_text, embedding
   FROM chunks
   WHERE document_id = ANY($2::uuid[]) AND embedding IS NOT NULL
 )
 SELECT id, document_id, page_number, chunk_text,
        1 - (embedding <=> $1::vector) AS score
 FROM candidates
 ORDER BY embedding <=> $1::vector
 LIMIT $3;

 $1 = question embedding, $2 = document id(s), $3 = how many (4 or 6)
 <=>  is pgvector's cosine DISTANCE operator (0 = same direction)
 score = 1 - distance = cosine SIMILARITY (higher = more relevant)

 Why "filter first, then exact search" (MATERIALIZED makes Postgres do the
 filter step first): a user's documents have at most a few thousand chunks,
 so exact ranking takes milliseconds and is always correct. An approximate
 index (HNSW / IVFFlat) is useful for millions of rows, but combined with a
 WHERE filter it can return fewer results than asked on older pgvector
 versions. Also, HNSW indexes on the plain vector type support up to 2000
 dimensions and our embeddings have 3072.

7.5 NORMALISATION
-----------------
 - Each fact stored once: user details only in users; document metadata only
   in documents; chunks reference documents by id.
 - Many-to-many (workspaces <-> documents) uses a separate link table with a
   composite primary key -> no duplicate links.
 - Repeating groups that are always read together and never queried
   individually (quiz questions, glossary, graph nodes) are stored as JSONB.
   This is a deliberate denormalisation: simpler code, one read per quiz.


================================================================================
8. KEY ALGORITHMS AND CONCEPTS
================================================================================

8.1 CHUNKING
------------
 Why: a whole document is too long to send with every question, and
 embeddings work best on focused passages.
 How: for each page, take 2000 characters, then move forward by 1800 so
 consecutive chunks share 200 characters (overlap).

   page text:  |-------- chunk 1 (0-2000) --------|
                                       |-------- chunk 2 (1800-3800) ------|
                                       <-200->
                                       overlap

 The overlap means a sentence cut at a boundary is still complete in one of
 the chunks. Chunks never cross pages, so each has one page number.
 (2000 chars is roughly 500 tokens: 1 token ~ 4 characters of English.)

8.2 EMBEDDINGS
--------------
 An embedding model turns text into a list of numbers (a vector) such that
 texts with similar MEANING get vectors pointing in similar directions.
 gemini-embedding-001 produces 3072 numbers per text.
   "Where does the Calvin cycle happen?"   and
   "The Calvin cycle takes place in the stroma"
 get similar vectors even though they share few exact words.
 This is what makes "semantic search" better than keyword search.

8.3 COSINE SIMILARITY
---------------------
 Measures the angle between two vectors A and B:

                        A . B            sum(Ai * Bi)
   cos(theta) = ----------------- = ------------------------------
                  |A| x |B|        sqrt(sum Ai^2) x sqrt(sum Bi^2)

   1  -> same direction (very similar meaning)
   0  -> unrelated
  -1  -> opposite
 Small example: A = (1, 2), B = (2, 4)  -> cos = 10 / (2.236 x 4.472) = 1.0
                A = (1, 0), B = (0, 1)  -> cos = 0
 pgvector's <=> returns cosine distance = 1 - cosine similarity.
 Cosine ignores vector length, which is what we want for comparing meaning.

8.4 RETRIEVAL-AUGMENTED GENERATION (RAG)
----------------------------------------
 1. Embed the question.
 2. Retrieve top-k similar chunks (k = 4 for one document, 6 for workspaces).
 3. Build a prompt with strict instructions + those chunks + the question.
 4. The model answers from the given context only; if the answer isn't in it,
    it must say so.
 Benefits: answers are grounded in the user's document, cite pages, work on
 documents of any length, and cost less than sending the whole document.

8.5 PROMPT DESIGN (how hallucination is reduced)
------------------------------------------------
 - "Use ONLY the context below. Do not use outside knowledge."
 - An exact fallback sentence for when the answer is missing.
 - Context passages are labelled with page numbers.
 - For structured outputs (quiz, summary, graph) we request JSON
   (responseMimeType: application/json), then validate it.

8.6 MAP-REDUCE SUMMARISATION
----------------------------
 Long documents don't fit in one prompt. MAP: summarise groups of 8 chunks
 (4 in parallel). REDUCE: summarise the summaries into the final structured
 summary.

8.7 EVEN SAMPLING FOR QUIZZES AND CONCEPT MAPS
----------------------------------------------
 Instead of the first 15 chunks, take 15 spread evenly from start to end:
 index_i = round(i x (n - 1) / 14) for i = 0..14. Questions cover the
 whole document.

8.8 MODEL FALLBACK AND RETRIES
------------------------------
 Gemini calls try models in order. On 503 (overloaded) or 429 (rate limit)
 the same model is retried once after 800 ms, then the next model is used.
 A model that returns 404 (doesn't exist) is skipped for the rest of the
 session. Embedding calls retry with increasing waits.

8.9 STREAMING (Server-Sent Events)
----------------------------------
 The server keeps the HTTP response open and writes events:
   event: sources   data: [{pageNumber, snippet, relevanceScore}, ...]
   event: delta     data: {"text": "The Calvin cycle "}
   event: delta     data: {"text": "takes place in the stroma..."}
   event: done      data: {"answer": "<full text>"}
 The browser reads the stream with fetch() and a ReadableStream and adds
 each piece to the message. First words appear as soon as the model writes
 them instead of after the whole answer.

8.10 "THINKING" LEVEL
---------------------
 Gemini 3 models can reason internally before answering. Useful for hard
 problems, but for answering from given passages it mostly adds delay, so
 the app sets the lowest level each model allows (MINIMAL / LOW, or a
 thinking budget of 0 for Gemini 2.5).

 - Hybrid search (keyword BM25 + vectors) and re-ranking for better retrieval
 - Evaluation set to measure answer accuracy automatically
 - HNSW index (with halfvec) for very large collections
 - Object storage (S3 / Cloudinary) for original files
 - Rate limiting per user; sharing workspaces between users
 - Follow-up questions that use previous chat turns as context

================================================================================
15. INTERVIEW QUESTIONS WITH ANSWERS
================================================================================

--- RAG and AI concepts ---

Q1. What is RAG?
A.  Retrieval-Augmented Generation: before the language model answers, we
    retrieve relevant information (here, passages from the user's document)
    and include it in the prompt, so the answer is based on that
    information instead of only the model's training data.

Q2. Why not just send the whole document to Gemini?
A.  Long documents may exceed the context limit, cost more, and are slower.
    Retrieval sends only the ~4 most relevant passages (~8,000 characters)
    regardless of document length, and lets me show exactly which passages
    were used.

Q3. What is an embedding?
A.  A list of numbers representing the meaning of a piece of text. Texts
    with similar meaning produce vectors pointing in similar directions. I
    use gemini-embedding-001, which outputs 3,072 numbers.

Q4. How do you find relevant chunks?
A.  I embed the question with the same model, then use pgvector's cosine
    distance operator (<=>) to rank that document's chunks and take the top
    4 (top 6 in workspaces).

Q5. What is cosine similarity and why use it?
A.  The cosine of the angle between two vectors: dot product divided by
    the product of their lengths. 1 means same direction. It compares
    direction (meaning) and ignores length, which is standard for text
    embeddings.

Q6. Why chunk the text? Why 2,000 characters with 200 overlap?
A.  Embeddings work best on focused passages, and we can only send a few
    passages to the model. 2,000 characters (~500 tokens) holds a complete
    idea; overlap keeps sentences that fall on a boundary complete in at
    least one chunk. Chunks never cross pages, so citations are precise.

Q7. How do you reduce hallucination?
A.  (1) The prompt says to use ONLY the provided context and gives an exact
    sentence to use when the answer isn't there. (2) Only relevant passages
    are given. (3) Sources are shown so the user can verify. It reduces the
    risk but can't make it zero - that's why citations matter.

Q8. What if the answer is spread across many parts of the document?
A.  Top-4 retrieval may miss some parts. Improvements: retrieve more chunks,
    hybrid keyword + vector search, or re-ranking. For whole-document tasks
    like summaries I don't use retrieval; I use map-reduce over all chunks.

Q9. Explain map-reduce summarisation.
A.  Map: summarise groups of 8 chunks separately (4 at a time in
    parallel). Reduce: combine those section summaries into the final
    overview, takeaways and glossary. It works for documents too long for
    one prompt.

Q10. How do you get reliable JSON for quizzes?
A.   I request JSON output (responseMimeType: application/json), strip
     markdown fences if present, accept either an array or an object
     wrapping one, and validate each question (options exist, correct
     answer index is valid) before saving.

Q11. What is the "thinking" setting and why did you lower it?
A.   Gemini 3 models can reason internally before answering. For answering
     from given passages that mainly adds latency, so I set the lowest
     thinking level each model allows. Together with streaming, this makes
     the first words of an answer appear much sooner.

Q12. What happens if Gemini is down or rate-limited?
A.   The client retries the same model once on 503/429, then falls back to
     the next model in a configurable list. Models that don't exist are
     skipped. The user gets a readable error if all fail.

--- Database and pgvector ---

Q13. Why PostgreSQL + pgvector instead of Pinecone / ChromaDB?
A.   Text, metadata, ownership and vectors are in the same row, so one SQL
     query can filter by user/document and rank by similarity, and deleting
     a document deletes its vectors via ON DELETE CASCADE in the same
     transaction. One database to run and back up. A separate vector DB
     makes sense at much larger scale.

Q14. Did you use a vector index (HNSW / IVFFlat)?
A.   No, deliberately. Search always filters to one user's documents first
     (a few thousand rows at most), and exact cosine ranking over those
     takes milliseconds and is always correct. Approximate indexes help with
     millions of rows, but combined with a WHERE filter they can return
     fewer than k results on older pgvector versions, and HNSW on the
     vector type supports at most 2,000 dimensions while my embeddings
     have 3,072. To scale, I'd use halfvec with an HNSW index and pgvector
     0.8 iterative scans.

Q15. Explain your schema.
A.   users -> documents (1:N) -> chunks with embeddings (1:N). Each document
     has chats -> messages, quizzes, a cached summary and a concept map.
     Workspaces link to documents through a many-to-many table
     workspace_documents with a composite primary key. All foreign keys
     cascade on delete. UUID primary keys.

Q16. Why UUIDs instead of auto-increment ids?
A.   They can be generated in Node before inserting, aren't guessable
     (users can't enumerate other ids), and are safe to expose in URLs.

Q17. Why JSONB for quiz questions?
A.   Questions are always read and written together with the quiz and never
     queried individually, so a JSONB column is simpler than a separate
     questions table. It's a deliberate denormalisation.

Q18. How do you prevent SQL injection?
A.   All queries are parameterised ($1, $2 ...); user input is never
     concatenated into SQL.

--- Backend ---

Q19. Why does upload return 202 and process in the background?
A.   Extraction and embedding can take several seconds for big files. The
     request returns immediately with status "processing"; the dashboard
     polls until it's "ready" or "failed".

Q20. How does streaming work?
A.   Server-Sent Events: the server sets Content-Type text/event-stream and
     writes events (sources, delta, done, error) as Gemini produces text.
     The browser reads it with fetch() and a ReadableStream (axios can't
     read streams in the browser). SSE is simpler than WebSockets for
     one-way server-to-client text.

Q21. How do you extract text from each format?
A.   PDF with pdf-parse (per page), DOCX with mammoth, Excel with SheetJS
     (per sheet), PPTX by opening the ZIP with JSZip and reading the text
     runs in each slide's XML, TXT directly.

Q22. How is authentication implemented?
A.   Passwords hashed with bcrypt. Login returns a JWT signed with a server
     secret (7-day expiry) containing the user id. The frontend sends it in
     the Authorization header; middleware verifies it and every query
     filters by that user id. Google sign-in verifies Google's ID token
     server-side before issuing our JWT.

Q23. JWT vs sessions?
A.   JWTs are stateless - no session store; any server instance can verify
     them. Downside: they can't be revoked before expiry without extra work
     (e.g. a denylist), which is why the expiry is limited.

Q24. How is one user prevented from seeing another's documents?
A.   Every query includes user_id from the verified token (e.g. WHERE id =
     $1 AND user_id = $2). Requests for someone else's id return 404 -
     tested in the automated tests.

Q25. How do you handle errors?
A.   Each route catches errors; a central Express error handler converts
     upload errors, invalid ids and unexpected errors into JSON with proper
     status codes; Gemini errors are turned into readable messages.

--- Frontend ---

Q26. How is state managed?
A.   React hooks (useState/useEffect) per page, plus Context for the logged-
     in user and the theme. The app is small enough not to need Redux.

Q27. How do you render the AI's Markdown safely?
A.   A small Markdown renderer that builds React elements (paragraphs,
     lists, tables, bold, code) instead of injecting HTML, so model output
     can't run scripts.

Q28. How does voice work?
A.   The browser's Web Speech API: SpeechRecognition turns speech into the
     question text; speechSynthesis reads answers aloud with adjustable
     speed. No server needed.

--- Design, scaling, improvement ---

Q29. How would you scale this to many users?
A.   Move background processing to a job queue (e.g. BullMQ + Redis) with
     workers; store original files in object storage; add an HNSW index
     with halfvec for large collections; cache embeddings of repeated
     questions; rate-limit per user; run multiple stateless API instances
     (JWT makes this easy).

Q30. How would you measure answer quality?
A.   Create a set of questions with known answers and pages; measure
     retrieval accuracy (is the right page in the top 4?) and answer
     correctness; re-run whenever chunk size, k or the prompt changes.

Q31. What was the hardest part?
A.   (Pick what is true for you.) e.g. getting reliable structured JSON
     from the model; making uploads robust across file types; designing the
     vector search to be both exact and fast; streaming answers through the
     stack.

Q32. What would you do differently?
A.   Add the evaluation set from the start, use a job queue for processing,
     and add hybrid search.

Q33. Why Gemini?
A.   Free tier suitable for a student project, a strong embedding model,
     fast Flash models, streaming and JSON output support in one SDK.

Q34. What are the limitations?
A.   No OCR for scanned PDFs; retrieval can miss information spread across
     many places; depends on Gemini availability and quota; free hosting
     sleeps when idle.
